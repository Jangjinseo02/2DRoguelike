# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

This is a **fresh Unity 6 (6000.4.2f1) 2D URP project skeleton**. Aside from Unity's
default assets there is no gameplay yet — `Assets/Scripts/Claude_Code.cs` is an empty
`MonoBehaviour` placeholder, and `Assets/Scenes/SampleScene.unity` is the only scene.
The roguelike itself is unimplemented, so most work starts from scratch.

## Working in this repo

There is no CLI build/lint/test wrapper — this project is driven from the Unity Editor
(open the folder with Unity Hub, editor version `6000.4.2f1` as pinned in
`ProjectSettings/ProjectVersion.txt`).

- **Solution:** `2DRoguelike.slnx` (new XML solution format) referencing the single
  Unity-generated `Assembly-CSharp.csproj`. Both `.csproj` and `.sln*` are gitignored
  and regenerated by Unity/the IDE integration; never hand-edit them or commit them.
- **C#:** LangVersion 9.0, `netstandard2.1`. Nullable reference types are not enabled.
- **Editor/debug:** VS Code is configured (`.vscode/launch.json` "Attach to Unity" via
  the `vstuc` debugger). The Rider and Visual Studio Unity packages are also installed.

### Building a player

Batch-mode build from a terminal (no editor UI), once a build script exists:

```
"<UnityEditor>/Unity.exe" -quit -batchmode -projectPath . -executeMethod <BuildClass.Method> -logFile -
```

There is currently no `Editor/` build script — add one under `Assets/**/Editor/` if
headless builds are needed.

### Running tests

`com.unity.test-framework` is a dependency but no tests or test assemblies exist yet.
To add them, create an assembly definition (e.g. `Tests/Tests.asmdef`) referencing
`UnityEngine.TestRunner` / `UnityEditor.TestRunner`. Run via the editor's Test Runner
window, or headless:

```
"<UnityEditor>/Unity.exe" -runTests -batchmode -projectPath . -testPlatform EditMode -testResults results.xml -logFile -
```

Use `-testPlatform PlayMode` for play-mode tests, and `-testFilter <fully.qualified.Name>`
to run a single test.

## Architecture notes

- **Single assembly.** No `.asmdef` files exist, so every script under `Assets/` compiles
  into `Assembly-CSharp`. Introducing assembly definitions (per feature: e.g. `Gameplay`,
  `Map`, `UI`) is the main lever for compile times and dependency boundaries as the
  codebase grows — decide the boundaries early.
- **Rendering:** Universal Render Pipeline, 2D renderer. Config lives in
  `Assets/Settings/` (`UniversalRP.asset`, `Renderer2D.asset`) and
  `Assets/UniversalRenderPipelineGlobalSettings.asset`. The 2D scene template is
  `Assets/Settings/Lit2DSceneTemplate.scenetemplate`.
- **Input:** the **new Input System** only (`ENABLE_INPUT_SYSTEM`). Bindings are in
  `Assets/InputSystem_Actions.inputactions`, with `Player` (Move, Look, Attack, Interact,
  Crouch, Jump, Sprint, Previous, Next) and `UI` action maps. Do not use the legacy
  `UnityEngine.Input` API.
- **2D toolchain available:** tilemap (+ extras), sprite animation, Aseprite importer,
  PSD importer, sprite shape — relevant for a tile-based roguelike map and animated
  sprites. Visual Scripting and Timeline are also installed.
- **Intended asset layout** (folders exist but are empty): `Assets/Scripts/`,
  `Assets/Prefabs/`, `Assets/ScriptableObjects/`, `Assets/Sprites/`, `Assets/Scenes/`.
  Consider ScriptableObjects for roguelike data (entity/item/enemy definitions, level
  generation parameters).

## Unity conventions

- Every asset has a sibling `.meta` file holding its GUID and import settings. When you
  add, move, rename, or delete an asset, the `.meta` must move with it — commit both.
  Prefer moving files via the Unity Editor so references stay intact.
- `Library/`, `Temp/`, `Logs/`, `UserSettings/`, and build output are gitignored
  (generated caches); `ProjectSettings/` and `Packages/` are committed.
- Scenes, prefabs, and `.asset` files are YAML but should be edited in the editor, not by
  hand — merge conflicts in them are painful, so keep changes small and coordinated.
